\section{The gap}
\label{sec:gap}

\begin{keyfinding}{The gap, in one sentence}
Bhoonidhi stores the footprint polygon of every scene it holds, and the only
question you are permitted to ask of that geometry is \emph{``does it touch
mine?''}
\end{keyfinding}

\subsection{How it was established}
\label{sec:methodology}

Three methods, each a script that saves its raw responses under
\code{docs/evidence/} so a reviewer can re-run it and diff the result.

\begin{enumerate}[leftmargin=1.8em]
  \item \textbf{Specification audit} (\code{probe\_gap.sh}) --- parses
    Bhoonidhi's \emph{own published API specification} and mechanically
    enumerates the spatial parameters, the absent predicates, the CQL2
    operations and any analysis vocabulary. Auditing the specification rather
    than the live service is the fairest reading --- it tests what NRSC says
    the API does --- and it is \textbf{reproducible offline}, which mattered
    because both NRSC hosts stopped answering from the build host partway
    through development.
  \item \textbf{Comparative baseline} (\code{probe\_baseline.sh}) --- probes
    ISRO's stack for any processing endpoint, then probes comparable EO
    portals live to test the obvious objection that nobody deploys this.
  \item \textbf{Cost measurement} (\code{measure\_redundancy.py}) --- asks this
    service's own \code{minimal-scene-set} the question the catalogue cannot
    answer, over four areas of interest and two collections.
\end{enumerate}

\textbf{What would falsify the claim}, stated in advance: any documented
spatial operator beyond intersection, any ISRO endpoint answering a processing
request, or a minimal covering set close in size to the candidate set. Each
script prints its own failure loudly rather than quietly passing.

\emph{access} gap.

\subsection{Why it is a large gap}

\subsubsection{An entire standardised tier is absent}

Server-side geospatial computation is not exotic. It has been an OGC standard
since \textbf{2007} (WPS 1.0.0, 05-007r7), with WPS 2.0 in 2015 and the modern
REST/JSON successor \textbf{OGC API --- Processes (18-062r2) in 2021}.
Bhoonidhi implements none of them. Probing ISRO's public stack:

\begin{lstlisting}
Bhuvan WPS 1.0.0 GetCapabilities       HTTP 404   absent
Bhuvan OGC API - Processes landing     HTTP 404   absent
Bhoonidhi /processes                   HTTP 404   absent
  MATCHED  no server-side computation anywhere in the public stack
\end{lstlisting}

So the missing thing is not a query parameter someone forgot. It is the whole
processing tier of the OGC stack, absent from India's national remote sensing
portal nearly two decades after it was standardised.

\begin{keyfinding}{The contrast}
Copernicus publishes \textbf{146} server-side processes at a public,
unauthenticated endpoint anyone can enumerate right now. Bhoonidhi publishes
\textbf{0}. That is not a scoping decision everyone else also made --- it is the
single capability separating Bhoonidhi from every portal it would be compared
against.
\end{keyfinding}

\begin{keyfinding}{The measured cost of the missing tier}
Across 8 queries the catalogue hands back \textbf{208 scenes}. \textbf{16} cover
the same ground to the same percentage. \textbf{192 are redundant --- 92\,\% of
everything returned}, or 206\,GB ordered where 16\,GB was required.
\textbf{And nothing in Bhoonidhi's API lets a user discover that.}
\end{keyfinding}

\textbf{Measured versus modelled:} the scene counts are measured live against
the running service over real STAC footprints --- that is the part carrying the
argument. The byte figures are published nominal product sizes multiplied by
those counts; the script never downloads imagery and says so in its own output.

\textbf{This is a floor, not a ceiling.} The footprint store holds 68 scenes
over a three-month window, so several rows are capped by the store rather than
by the AOI. A real archive spans decades with many revisits per year: it returns
far more intersecting scenes for the same AOI while the number needed to cover
it stays roughly constant. \textbf{Redundancy rises with archive depth.}

\subsubsection{The workaround is expert-only, so nobody does it}

The honest objection is \emph{``you can just do this yourself''}. True --- and
that is the gap. To learn the 92\,\% figure for their own AOI a user must:
search and page through every result; extract each footprint; load 30+ polygons
into a GIS or a \code{shapely} script; union them and difference against the
AOI; \textbf{reproject to an equal-area CRS or every area is wrong}; implement a
\textbf{set-cover optimisation} (NP-hard~\cite{setcover}); and map the result
back to orderable item ids.

That is a GIS-literate programmer's afternoon, repeated for every AOI, by every
user --- and it is the same seven steps every time, over geometry the server
already holds in memory when it answers the search. So in practice nobody does
it. They download all 30 scenes. \textbf{This service does all seven steps in
one HTTP request} (Section~\ref{sec:results}).

\subsection{Scope of the claim}

\textbf{Claimed:} Bhoonidhi has no server-side spatial computation; that
capability is standardised, deployed by peers, and its absence has a measurable
cost; a conformant OGC API --- Processes service closes it.

\textbf{Not claimed:} that Bhoonidhi is badly built (discovery is solved), that
authentication is wrong, that this project's footprints \emph{are} Bhoonidhi's
(they are substituted and flagged --- Section~\ref{sec:limitations}), or that
this is an official NRSC product.
